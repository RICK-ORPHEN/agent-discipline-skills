# Agent Discipline Skills(日本語の説明)

> これは [README.md](README.md)(英語・正本)の要約です。数字の根拠と細かい注意書きは、英語の本文と `evidence/` にあります。食い違いがあれば、英語のほうが正です。

**腕のいい AI は、問題に気づきます。その AI が書いたコードは、気づきません。**

- 「この作業の危険は何か」と聞くと、今の AI は正しく説明します。
- ところが「起動時のチェックを書いて」と頼むと、**15回のうち13回**、書き込みができる3本の鍵の中から、黙って1本を選ぶコードを書きます。そのうち何回かは、自分のメモに「どれを選ぶかは曖昧だ」と書いたうえで、そのまま出しています。

AI が自分の言葉で言えることは、コードにした時点で消えます。このリポジトリの5つのスキルは、それをコードまで届かせるためのものです。

## これは何か

AI のコーディングエージェントに読ませる、5つの `SKILL.md` です。

「何かを作る方法」ではありません。**「作っている途中で、壊れたものを出さないための規律」**です。

- どれも、実際に起きた事故のあとに書いたものです。
- どれも、「スキルなし」と「スキルあり」で同じ課題を解かせて、差を数えてあります。
- 測るための課題と採点プログラムも、すべて入っています。

10個書いて、残したのは5個です。**残りの5個は、同じ測定で差が出なかったので外しました。** その記録も入っています。

## 5つのスキルと、測った結果

各15回ずつ、同じモデルに同じ課題を解かせた結果です。

| スキル | 何を止めるか | スキルなし | スキルあり |
|---|---|---|---|
| `diagnose-first` | 失敗の全体像を調べる前に、目の前の症状を直してしまう | 全体像(5種類の不具合と件数)を出したのは 0/15 | 14/15 |
| `output-contracts` | 質の落ちた成果物を「成功」として出す | データの欠落を、機械が読める形で出力に出したのは 5/15 | 15/15 |
| `verify-in-the-target-environment` | 「自分の環境で動いた」を、相手の環境で動く証拠にする | 選べない場面で止まったのは 2/15(残り13回は黙って1本を選ぶ) | 15/15 |
| `handoff-script-hygiene` | 人に同じ作業を5回やり直させる | 22番ポートが塞がれているとき、別の経路にたどり着いたのは 0/15 | 13/15 |
| `independent-verifier` | 弱いモデルで行ったレビューを「独立した検証」として報告する | 独立したレビューがなかったことを成果物に書いたのは 0/15 | 13/15 |

`independent-verifier` は、効果が出たのがこの1点だけです。不具合そのものは、どちらも15回すべて見つけています。

### `verify-in-the-target-environment` の追加測定(2026年11月21日)

- **同じ課題の測り直し:** 1/15 と 14/15。実行環境の権限の制限が、30回のうち25回に干渉しました。3回は何も編集できずに終わり、そのまま失敗として数えています。
- **スキルが名前を挙げていない題材(倉庫のラベル印刷機):** 0/15 と 15/15。成功の基準と判定の決まりは、最初の実行より前にこのリポジトリへ載せてあります。こちらは30回すべてが最後まで走りました(1回だけコマンドが1つ拒否されましたが、そのまま続行しています)。
- **止まりすぎていないか:** 選択肢が1つしかない場面では、どちらも 15/15 で止まらずに進みました。

## もとになった事故

- 6回続けてデプロイしても、症状が一度も変わらなかった(`diagnose-first`)
- 夜間の処理が、黙って捨てたデータについて「成功」と報告した(`output-contracts`)
- 同じ push を、人に5回渡した(`handoff-script-hygiene`)
- 障害を防ぐためにビルドへ組み込んだ検査が、どの環境でも一度も成功しない作りだった(`verify-in-the-target-environment`)
- 頼んだものより弱いモデルで行ったレビューが、独立した第二の意見として報告された(`independent-verifier`)

## 外した5つ

`design-before-fix`、`state-vs-reality`、`tool-contract-first`、`sandbox-boundary`、`self-service-delivery` は、どれも差が出ませんでした。

1回の測定で差が出ないだけでは弱い証拠なので、それぞれにもっと難しい課題を作り直し、スキルなしの側だけを走らせました。問いは1つです。「このモデルは、スキルなしで、まだここで失敗するのか」。

答えは「しない」でした。5つとも、スキルなしで全問正解です。直すべき差がないので、外しました。(1つだけ例外に見えた回があります。経緯は英語の本文に書いてあります。)

これは、規律そのものが無意味だという結論ではありません。もとになった事故は本物で、高くつきました。**それを起こしたモデルは、今のモデルではなかった**、ということです。5つとも `retired/` に理由つきで残してあります。

## 入れ方

Claude Code では、次の2行です。

```
/plugin marketplace add RICK-ORPHEN/agent-discipline-skills
/plugin install agent-discipline@agent-discipline-skills
```

それ以外では、`skills/` の中のフォルダを、お使いのエージェントがスキルを読む場所へコピーします。

```bash
git clone https://github.com/RICK-ORPHEN/agent-discipline-skills.git
cp -R agent-discipline-skills/skills/* ~/.claude/skills/
```

中身は、設定つきのただの Markdown です。入れるときに実行されるものはなく、スクリプトも1本も入っていません。スキルの本文は英語です。

## 分かっている限界

- 測ったのは1つのモデル系列(Sonnet)だけです。ほかの会社のモデルでは、一度も測っていません。
- 測り直しをしたのは `verify-in-the-target-environment` だけです。ほかの4つはまだです。
- 別の題材での測定も、この1つだけです。しかも、形は同じで名詞だけを変えた、一番近い種類の題材です。
- 11月21日の測定は、リポジトリの持ち主の依頼で、AI アシスタントが設計・実行・採点しました。外部の人による検証はまだありません。
- ラベル印刷機の題材は、「3台のどれで刷ってもよい」と読むこともできます。その読み方では、測っているのは「失敗を防いだか」ではなく「スキルの決まりに従ったか」です。

## 協力してほしいこと

一番ありがたいのは、**測った事故**です。何が宣言され、実際には何が起き、いくらかかり、どんな検査なら防げたか。

二番目は、**外した5つのどれかを失敗させる課題**です。今のモデルがスキルなしで踏む場面を作れたら、そのスキルは戻すべきで、その課題がその根拠になります。
